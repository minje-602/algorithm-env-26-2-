# 힙 정렬 학습 정리

> 과제 요구사항 중 "배우지 않은 정렬은 이게 어떤 것인지 AI를 통해서 학습한 내용을
> 첨부" 에 해당하는 문서다. 구현을 쓰기 전에 먼저 정리했고, 정리하면서 세운 가설은
> 이후 실험에서 실제로 측정해 확인했다. 확인 결과는 각 절 끝에 함께 적었다.

---

## 1. 한 줄로 말하면

**힙 정렬(Heapsort)은 선택 정렬에서 "최대값 찾기"만 바꾼 정렬이다.**

선택 정렬은 남은 구간을 처음부터 끝까지 훑어 최대값을 찾는다. 원소가 n개면 한 번
찾는 데 O(n)이고, 이걸 n번 반복하니 O(n²)이 된다. 이 구조에서 바꿀 수 있는 곳은
한 군데뿐이다 — **최대값을 더 빨리 찾을 수 있다면?**

힙 정렬의 답은 "배열을 최대 힙으로 유지하면 최대값은 항상 맨 앞에 있고, 하나를
빼낸 뒤 복구하는 데 O(log n)이면 된다" 이다. O(n)이 O(log n)이 되니
전체가 O(n²)에서 O(n log n)으로 내려간다.

그래서 힙 정렬은 새로운 발상이라기보다, **선택 정렬의 병목에 적절한 자료구조를
끼워 넣은 결과**로 이해하는 편이 정확하다. Topic 01에서 "알고리즘은 적절한
자료구조를 필요로 한다"고 했던 것의 교과서적 사례이기도 하다.

---

## 2. 힙이란 무엇인가

### 2.1 배열을 트리로 읽는 규칙

힙은 별도의 자료구조를 만드는 게 아니라 **배열을 트리로 해석하는 약속**이다.
인덱스 `i`에 대해

```
왼쪽 자식 = 2i + 1
오른쪽 자식 = 2i + 2
부모 = (i - 1) / 2
```

배열 `[9, 7, 8, 3, 5, 1, 2]`를 이 규칙으로 읽으면 이렇게 된다.

```
          9(0)
        /      \
     7(1)      8(2)
     /   \     /   \
  3(3)  5(4) 1(5)  2(6)
```

포인터도 노드 객체도 없다. **인덱스 산술만으로 트리가 성립한다.** 힙 정렬이
추가 메모리 없이 도는 근본 이유가 여기 있다.

### 2.2 힙 성질

최대 힙(max-heap)의 조건은 하나뿐이다.

> 모든 부모는 자기 자식보다 크거나 같다.

주의할 점은 이게 **정렬이 아니라는** 것이다. 위 예시에서 레벨 2의 `3, 5, 1, 2`는
서로 순서가 없다. 힙이 보장하는 건 오직 "루트가 전체 최대값"이라는 사실 하나다.
정렬보다 약한 조건이라서 유지 비용이 싸고, 그 약한 보장만으로도 정렬을 만들 수
있다는 게 이 알고리즘의 요점이다.

## 3. siftDown — 핵심 연산 하나

힙 정렬에서 실제로 일하는 함수는 `siftDown` 하나뿐이다. 나머지는 전부 이걸
언제 몇 번 부르느냐의 문제다.

**상황**: 어떤 노드의 두 서브트리는 이미 힙인데, 그 노드 자신만 힙 성질을 어기고
있다. **할 일**: 그 노드를 제자리까지 끌어내린다.

```
1. 두 자식 중 더 큰 쪽을 고른다          (비교 1회)
2. 그 자식이 나보다 크면 교환하고 내려간다  (비교 1회)
3. 아니면 멈춘다 — 제자리를 찾았다
```

두 가지를 짚어둘 필요가 있다.

**왜 더 큰 자식과 교환해야 하는가.** 작은 자식과 바꾸면 올라간 그 작은 값이 다른
자식보다 작아져 힙 성질이 다시 깨진다. 큰 쪽을 올려야 양쪽 모두를 만족시킨다.

**레벨당 비교가 2회다.** 자식끼리 한 번, 부모-자식 한 번. 이 숫자가 나중에 힙
정렬의 비교 횟수를 결정한다 (→ 5.3절).

---

## 4. 두 단계

### 4.1 1단계 — 힙 구성 (heapify)

```
for i = n/2 - 1 downto 0:
    siftDown(i, n)
```

`n/2 - 1`부터 시작하는 이유는, 그 뒤의 인덱스들은 전부 **잎 노드**라서 자식이 없고
따라서 이미 그 자체로 힙이기 때문이다. 손댈 필요가 없다.

거꾸로 내려가는 이유는 `siftDown`의 전제 조건 때문이다. `siftDown(i)`는 "i의 두
서브트리는 이미 힙"임을 가정하는데, 뒤에서부터 처리하면 i를 다룰 시점에 그 아래는
전부 처리가 끝나 있다.

### 4.2 2단계 — 정렬

```
for end = n-1 downto 1:
    swap(a[0], a[end])    # 최대값을 확정된 자리로
    siftDown(0, end)      # 힙 크기를 하나 줄이고 복구
```

배열이 두 구역으로 나뉘어 자란다. 앞쪽 `[0, end)`는 아직 힙이고, 뒤쪽
`[end, n)`은 **이미 정렬이 끝나 다시 건드리지 않는 구간**이다. 매 회전마다 힙에서
가장 큰 값이 빠져나와 정렬 구간의 맨 앞에 붙으므로, 뒤쪽 구간은 항상 오름차순을
유지한다.

## 5. 복잡도

### 5.1 힙 구성이 O(n)인 이유

직관적으로는 "n/2개 노드 각각에 O(log n)이니 O(n log n)" 같지만, 실제로는
**O(n)** 이다. 대부분의 노드가 트리 아래쪽에 있어 끌어내릴 거리가 짧기 때문이다.

높이 h인 노드는 최대 `n/2^(h+1)`개이고, 각각의 작업량은 O(h)다.

```
전체 = Σ (n / 2^(h+1)) · h  =  (n/2) · Σ h/2^h
```

`Σ h/2^h`는 h=0부터 무한대까지 더해도 **2로 수렴**한다. 따라서 전체는 O(n)이다.

바꿔 말하면 잎에 가까운 절반은 아예 움직이지 않고, 그 위 1/4은 많아야 한 칸,
그 위 1/8은 많아야 두 칸 내려간다. 이 급수가 유한하게 닫혀서 선형이 된다.

### 5.2 정렬 단계가 O(n log n)인 이유

`siftDown`을 n-1회 부르고 각각 최대 log n 깊이니 O(n log n)이다. 여기엔
최선·최악의 구분이 없다 — 입력이 어떻게 생겼든 트리 높이는 log n이고 매번 루트를
바닥까지 내려보내는 구조라서, **입력 모양에 거의 영향을 받지 않는다.**

이게 퀵 정렬과 갈리는 지점이다. 퀵은 운이 나쁘면 O(n²)로 무너지지만 힙은 그럴
입력이 없다. 전체 복잡도는 O(n) + O(n log n) = **O(n log n)**, 최선·평균·최악이
모두 같다.

### 5.3 비교 횟수는 병합 정렬의 약 2배

3절에서 본 대로 `siftDown`은 레벨당 비교를 2회 한다. 깊이가 log n이니 한 번
호출에 약 2 log n회, 이걸 n번 하면 **약 2n log₂n**회다. 병합 정렬이 약
`n log₂n - n`회이므로 대략 두 배가 된다.

같은 O(n log n)이라도 **상수가 다르다**는 뜻이고, 이건 점근 표기가 감추는
정보다 (Topic 05).

**확인**: 무작위 입력으로 실제 비교 횟수를 세어 이론 근사값
`2n log₂n - 2n log₂e`와 대조했다.

| n | 실측 비교 | 이론 근사 | 비율 |
|---:|---:|---:|---:|
| 1,000 | 16,828 | 17,046 | 0.987 |
| 4,000 | 83,491 | 84,185 | 0.992 |
| 8,000 | 183,036 | 184,369 | 0.993 |
| 32,000 | 859,951 | 865,478 | 0.994 |

오차 1% 이내이고 n이 커질수록 1에 수렴한다. 이론식이 맞다고 볼 수 있다.

---

## 6. 공간이 O(1)인 이유

2.1절에서 본 대로 트리가 인덱스 산술로만 표현되므로 노드 객체도 포인터도 없다.
그리고 `siftDown`을 **반복문으로 작성하면 재귀 스택도 쓰지 않는다.** 실제로 필요한
추가 공간은 교환에 쓰는 임시 변수 한 칸뿐이다.

병합 정렬이 O(n) 보조 배열을 요구하고 퀵 정렬이 O(log n) 재귀 스택을 쓰는 것과
대비된다. 세 정렬 중 공간 면에서는 힙이 가장 저렴하다.

## 7. 왜 불안정한가

**최소 반례가 n = 2다.** 직접 돌려 확인했다.

```
입력:  [(1, a), (1, b)]      ← 값이 같고 a가 먼저
출력:  [(1, b), (1, a)]      ← 순서가 뒤집혔다
```

원인은 2단계의 `swap(a[0], a[end])`가 **무조건 교환**이기 때문이다. 값이 같은지
따지지 않고 루트와 마지막 원소를 맞바꾼다. n=2라면 힙 구성 단계에서 아무 일도
일어나지 않고, 정렬 단계의 첫 교환이 그대로 두 원소를 뒤집어 버린다.

일반적으로도 이 교환은 **멀리 떨어진 두 원소를 맞바꾸는** 연산이다. 안정성이
깨지는 전형적인 조건(선택 정렬이 불안정한 것과 같은 이유)에 정확히 해당한다.
병합 정렬이 인접한 두 조각을 순서대로 이어붙이며 `<=`로 왼쪽을 우선하는 것과
구조적으로 다르다.

이걸 고치려면 각 원소에 원래 인덱스를 덧붙여 비교 기준을 (값, 인덱스)로 바꾸는
방법이 있지만, 그러면 O(n) 추가 공간이 필요해져 힙 정렬의 장점인 O(1)이 사라진다.
**안정성과 제자리성을 동시에 갖기 어렵다**는 트레이드오프가 여기서 드러난다.

## 8. 이론이 같은데 실측이 느린 이유

세 정렬이 모두 평균 O(n log n)이지만, 실제로 돌려보면 힙 정렬이 대체로 가장
느리다. 위키피디아도 "잘 구현된 퀵 정렬이 보통 힙 정렬보다 2~3배 빠르다"고 적고
있다. 이유는 두 가지다.

첫째는 5.3절의 **상수 차이** — 비교를 두 배 한다.

둘째가 더 중요한데 **캐시 지역성**이다. `siftDown`은 인덱스 i에서 2i+1로
건너뛰며 내려간다. n이 커지면 이 점프 폭이 캐시 라인을 훌쩍 넘어서, 한 번 내려갈
때마다 새로운 캐시 미스가 난다. 반면 병합 정렬은 두 구간을 앞에서부터 순차적으로
읽고, 퀵 정렬의 파티션도 양끝에서 안쪽으로 순차 접근한다. **둘 다 하드웨어의
prefetch가 잘 먹는 패턴이고, 힙만 그렇지 않다.**

점근 표기는 메모리 계층을 모르는 모델 위에서 정의된 것이라, 이 차이를 표현할
방법이 없다. 그래서 O(n log n) 세 개가 같아 보이지만 실측은 갈린다.

## 9. 역사와 변형

**1964년, J. W. J. Williams**가 이진 힙과 함께 힙 정렬을 발표했다. 같은 해
**Robert W. Floyd**가 제자리 정렬이 가능하도록 개선했는데, 5.1절의 O(n) 힙
구성이 그의 기여다.

파생된 것들 중 이 과제와 관련 있는 것은 두 가지다.

**Bottom-up heapsort**는 비교 횟수를 평균 `2n log₂n`에서 `n log₂n` 수준으로
줄인 변형이다. 다만 현대 CPU의 분기 예측 때문에 정수 키에서는 이 이점이 상쇄된다는
보고가 있다.

**Introsort**는 퀵 정렬로 시작해 재귀 깊이가 일정 한계를 넘으면 힙 정렬로
갈아타는 하이브리드다. 퀵의 평균 속도와 힙의 최악 보장을 둘 다 가져가는
설계이고, C++ 표준 라이브러리의 `std::sort`가 이 방식이다. **이번 과제에서
비교할 세 정렬의 관계를 실무가 어떻게 정리했는지 보여주는 사례**라서, 보고서
결론에서 언급할 만하다.

## 10. 세 정렬 안에서의 위치

| | 최악 시간 | 추가 공간 | 안정성 | 입력 의존성 |
|---|---|---|---|---|
| 퀵 | O(n²) ✗ | O(log n) | ✗ | 큼 (피벗·중복에 취약) |
| 병합 | O(n log n) | O(n) ✗ | ○ | 작음 |
| 힙 | O(n log n) | O(1) | ✗ | 거의 없음 |

세 정렬이 **각자 서로 다른 하나씩을 포기하고 있다.** 퀵은 최악 보장을, 병합은
공간을, 힙은 안정성과 실측 속도를 내준다. 공짜로 다 가질 수 없다는 것이 이
비교의 결론이 될 것 같다.

## 11. 학습 방법과 검증

이 문서는 Claude(Anthropic)와의 대화로 학습한 내용을 정리한 것이며, 아래 방식으로
사실 확인을 거쳤다.

- 복잡도·역사·변형에 관한 서술은 위키피디아
  [Heapsort](https://en.wikipedia.org/wiki/Heapsort) 문서와 대조했다.
- 5.3절의 비교 횟수 이론값은 실제로 힙 정렬을 구현해 카운터를 세고 이론 근사식과
  대조해 오차 1% 이내임을 확인했다.
- 7절의 불안정성 최소 반례는 n=2~6의 모든 입력을 전수 탐색해 가장 작은 것을
  찾은 결과다.

즉 AI가 준 설명을 그대로 옮기지 않고, **검증 가능한 주장은 직접 측정해 확인한 뒤**
서술했다.
